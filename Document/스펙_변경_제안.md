# 스펙 변경 제안 (v1.3) — 2026-09-02

`Document/API_명세서_V2.pdf`(v1.2)와 `Document/요구사항_명세서_V2.pdf`(v1.2)를 실제 구현(A/B/C/D 감사
전체 반영, [[api-spec-compliance-audit]] 참고)과 맞추기 위한 변경 제안입니다. PDF를 직접 수정할 수는
없어 이 문서를 원본에 옮겨 적는 용도로 작성했습니다 — 섹션 번호는 두 PDF의 현재(v1.2) 목차 기준입니다.

핵심 요약: **API 레벨의 실제 동작은 이제 API 명세서 v1.2와 거의 완전히 일치합니다.** 남은 차이는
④ 이메일 발송 미구현(의도적 축소), ⑤ `/students/{id}/summary` 권한 범위가 표보다 넓음(의도적 확장,
문서 쪽 정의가 애초에 두 화면을 겸용하고 있었다는 사실이 드러난 것) 두 가지뿐입니다.

## 1. `API_명세서_V2.pdf` 변경 제안

### 1.1 §2.2 인증 — 변경 없음(이미 맞음)
"Authorization: Bearer {accessToken} 헤더로 인증... 서버가 매 요청마다 역할 기반 접근 제어(RBAC)를
수행" — 문서 그대로 구현되었습니다. 확인 문구만 추가 권장: *"(v1.3, 2026-09-02부터 실제 구현·강제됨)"*

### 1.2 §3 인증 API — "구현 완료" 표시 + 세부 사항 추가

| Method | Path | 구현 상태 |
|---|---|---|
| POST | `/auth/login` | 구현 완료 |
| POST | `/auth/logout` | 구현 완료 |
| POST | `/auth/refresh` | 구현 완료 |
| POST | `/auth/password/reset-request` | **부분 구현** — 아래 참고 |
| POST | `/auth/password/reset` | **부분 구현** — 아래 참고 |
| GET | `/me` | 구현 완료 |

추가할 문구(§3 하단, 기존 요청/응답 예시 뒤):

> **v1.3 구현 노트**
> - Access Token 만료 30분, Refresh Token 만료 14일. Refresh Token은 서버에 해시로 저장되어
>   재발급 시 로테이션(기존 토큰 폐기 후 신규 발급)되고, `/auth/logout` 호출 시 폐기된다 —
>   §16.2의 "토큰 만료 시간 및 Refresh Token 정책" 미정 사항이 이렇게 확정되었다.
> - **`/auth/password/reset-request`/`/auth/password/reset`은 이메일 발송 인프라(SMTP 등)가 없어
>   토큰 발급·소비 로직만 구현되어 있다.** `reset-request` 응답에 재설정 토큰이 이메일 대신 직접
>   노출되는데, 이는 **개발/테스트 전용 임시 조치이며 운영 배포 전 반드시 이메일 발송으로 교체하고
>   응답에서 토큰을 제거해야 한다.** 그 전까지 실질적인 "비밀번호 분실 시 재설정"(REQ-AUTH-07)
>   경로는 관리자 초기화(`POST /users/{id}/reset-password`)를 쓴다.
> - `User` 엔티티에 email 컬럼이 없다(요구사항 명세서 §6 데이터 모델에도 없음) — 이메일 발송을
>   실제로 붙이려면 `User.email` 컬럼 추가가 선행되어야 한다(ERD 변경 필요).

### 1.3 §8 학부모·자녀 연결 API — 경로가 명세서와 완전히 일치하게 됨
`GET /me/children`이 이제 실제로 그 경로로 구현되어 있습니다(예전엔 `/v1/parents/{parentUserId}/children`
로 대체돼 있었음). 표/설명 변경 불필요 — 이미 맞습니다.

### 1.4 §14 공지사항 API — 경로 일치 + X-Active-Student-Id 동작 확정
`GET /me/notices`도 이제 그 경로로 구현되어 있습니다. `X-Active-Student-Id` 헤더 동작도 문서 설명과
일치합니다: 학부모가 헤더를 생략하면 **첫 번째 자녀**를 기본값으로 사용하도록 확정되었습니다 —
문서에는 이 기본값 규칙이 없어 다음 문구 추가를 제안합니다:

> `X-Active-Student-Id`를 생략하면 서버는 학부모의 자녀 중 첫 번째(연결 순서 기준)를 기본값으로
> 사용한다. 활성 자녀를 명시했는데 본인 자녀가 아니면 403 `FORBIDDEN_SCOPE`.

### 1.5 §15 권한 매트릭스 — "구현 완료" 표시
전체 표가 실제로 서버에서 강제됩니다(역할 체크는 `FORBIDDEN_ROLE`, 범위 체크는 `FORBIDDEN_SCOPE`).
각주 문구("모든 '담당만'/'자녀만'/'본인만' 범위 제한은... 403으로 거부하는 것을 원칙으로 한다")도
그대로 지켜졌습니다 — 응답 필터링이 아니라 요청 단계에서 거부합니다(단, `GET /notices`의 목록
필터링은 예외로 문서화 필요 — 아래 1.6 참고).

### 1.6 §15 매트릭스에 없던 세부 규칙 — 문서에 명문화 필요

1. **`GET /students/{id}/summary`의 실제 허용 범위가 §5 표보다 넓습니다.** §5는 이 엔드포인트를
   SCR-11(선생님용 학생 상세)로만 정의해 `admin, teacher(담당)`만 명시하지만, FR-07-01(학부모/학생
   홈 요약)에 대응하는 별도 엔드포인트가 명세서에 없어서 실제로는 이 API가 두 화면을 겸용하고
   있습니다. 구현은 `admin, teacher(담당), parent(자녀), student(본인)`까지 허용합니다. **제안:**
   §5 표의 권한 칸을 `admin, teacher(담당), parent(자녀), student(본인)`으로 수정하거나, FR-07-01
   전용 엔드포인트(예: `GET /me/summary`)를 신설해 SCR-11과 분리할지 결정이 필요합니다.
2. **`GET /notices`(목록)는 teacher일 때 응답을 필터링합니다** — `classId`를 지정하면 그 반을
   담당하지 않을 경우 403이지만, `classId` 없이 호출하면(전체 조회) admin과 달리 teacher는
   "scope=all 전체 + 본인이 담당하는 반들"만 걸러서 돌려줍니다(§15 각주의 "필터링 아닌 거부" 원칙의
   유일한 예외 — 목록 API라 완전 거부보다 필터링이 자연스럽다고 판단). §14 표에 이 필터링 규칙을
   명문화하는 것을 제안합니다.
3. **`PATCH`/`DELETE /notices/{id}`, `PATCH /notices/{id}/pin`**은 "teacher(본인이 작성한 담당
   반 공지만)"을 문자 그대로 강제합니다 — 작성자 본인이면서 **지금도** 그 반을 담당해야 통과합니다
   (담당이 바뀌면 예전 작성자라도 더 이상 수정 불가). 표에는 이미 이렇게 쓰여 있어 변경 불필요,
   확인만.

### 1.7 §16.2 확인 필요 사항 — 해결된 항목 표시

| 항목 | 상태 |
|---|---|
| 인증 방식: JWT 자체 발급 vs. 외부 Auth 서비스 | **해결 — JWT 자체 발급**(외부 서비스 미사용) |
| 토큰 만료 시간 및 Refresh Token 정책 | **해결 — Access 30분 / Refresh 14일, 로테이션 방식** (1.2 참고) |
| bulk 저장 시 일부 실패 처리 방식 | **사실상 해결 — 전체 롤백.** 각 bulk 엔드포인트가 단일 `@Transactional` 메서드라 예외 발생 시 그 요청 전체가 롤백된다. 부분 성공이 필요하면 별도 설계가 필요하다는 점은 문서에 명시할 가치가 있음 |
| 파일/이미지 업로드 필요 여부 | 미해결 (범위 밖 유지) |
| 실시간 반영 방식(polling vs 웹소켓) | 미해결 — 현재 프런트엔드는 재조회(polling) 가정으로 구현 범위 밖 |

## 2. `요구사항_명세서_V2.pdf` 변경 제안

### 2.1 §3.1 권한 관련 요구사항 — 전부 "구현 완료"로 표시

| ID | 상태 / 구현 노트 |
|---|---|
| REQ-AUTH-01 (4역할 RBAC) | 구현 완료 — JWT payload의 `role` claim 기준 |
| REQ-AUTH-02 (선생님 담당 범위 제한) | 구현 완료 — `SchoolClass.teacher` + `TeacherAssignment`(반/학생 단위 추가 배정) 둘 다로 담당 여부 판단 |
| REQ-AUTH-03 (학부모 다자녀, 자녀 선택 전환) | 구현 완료 — `X-Active-Student-Id` 헤더 + 로그인 응답의 `hasMultipleChildren` 플래그 |
| REQ-AUTH-04 (학생은 조회만) | 구현 완료 — student 역할은 모든 쓰기 API에서 `FORBIDDEN_ROLE` |
| REQ-AUTH-05 (관리자의 계정 관리) | 구현 완료(FR-01 시점부터 이미 구현되어 있었음) |
| REQ-AUTH-06 (아이디/비밀번호 로그인, 비밀번호 암호화) | 구현 완료 — BCrypt |
| REQ-AUTH-07 (비밀번호 분실 재설정) | **부분 구현** — 관리자 초기화는 완전 구현, 이메일 자가 재설정은 토큰 발급까지만(1.2 참고) |

### 2.2 §1.4 문서 개정 이력 — v1.3 항목 추가 제안

```
v1.3   2026-09-02   ① REQ-AUTH-01~07 구현 완료 반영 ② API 명세서 §3 인증 API/§15 권한
                    매트릭스 "구현 완료" 표시, 토큰 정책(Access 30분/Refresh 14일, 로테이션)
                    확정 ③ 비밀번호 자가 재설정은 이메일 인프라 부재로 토큰 발급까지만 구현되어
                    있음을 명시(REQ-AUTH-07 부분 구현) ④ GET /dashboard/teacher 응답을
                    myClasses/allClassesSummary 방식으로 API 명세서와 일치시킴(2026-09-02,
                    이전 v1.2는 "미입력 항목 카운트" 방식이었음) ⑤ GET /students/{id}/summary가
                    SCR-11 외에 FR-07-01(학부모/학생 홈 요약)도 겸용하고 있음을 명시 —
                    API 명세서 §5 권한 칸 수정 필요(위 1.6-1 참고)
```

### 2.3 §9 확인 필요 사항 — 변경 없음
이 섹션의 항목(학생 규모, 테스트 점수 체계, 문항 유형 카테고리, 점수대 구간, 실제 도메인/호스팅,
개발 일정)은 인증과 무관해 그대로 둡니다.

## 3. 남은 갭 요약 (D 버킷 — 의도적, 막지 않음)

- `GET /dashboard/classes`, `GET /v1/students/{id}/notifications/badge`(FR-08) — 명세서에 대응
  엔드포인트가 아예 없는 추가 기능. 해가 없어 유지.
- `/notices`, `/students/{id}/summary`의 `limit` 쿼리 파라미터 — 명세서에 없지만 편의상 추가.
- 위 1.6-1의 `/students/{id}/summary` 권한 확장.

이 문서에 반영된 변경을 실제 PDF에 옮겨 적으면 API 명세서/요구사항 명세서 모두 v1.3으로
버전업하는 것을 제안합니다(두 문서 모두 현재 v1.2).
