# 1차 피드백 대응 정리 (Document/1차 피드백/1차 피드백.hwp 기준)

원본 hwp의 피드백 4건 중 1번은 백엔드에서 고쳤고, 2·3·4번은 프론트에서 처리해야 합니다.
(4번은 백엔드에서 재현이 안 돼서 프론트 쪽 확인 포인트를 같이 적었습니다.)

## 1. 학부모-자녀 연결 — 백엔드 수정 완료 ✅

**원래 피드백**: "오지훈 학생에 엄마 한 명만 연결되어 있는데 Admin계정에서 연결할 수 없다고 뜸.
그리고 신도현 학생에는 Mother가 두 명 있음."

**원인**: `POST /v1/parent-links`가 같은 학부모-학생 쌍의 중복만 막고, "엄마/아빠가 이미 있는데 또
엄마/아빠로 연결"하는 건 막지 않고 있었습니다. 그래서 실수로 같은 학생에 엄마가 둘 연결될 수
있었습니다(신도현 케이스가 실제로 그랬음 — DB에서 확인).

**수정**: 한 학생당 `father`/`mother`는 각각 최대 1명만 연결되도록 서버에서 막았습니다
(`other`는 조부모 등 여러 명 있을 수 있어 제한 없음). 이미 있는 관계로 또 연결/변경하려 하면:

```json
// POST 또는 PATCH /v1/parent-links, 422
{ "error": { "code": "VALIDATION_ERROR", "message": "이미 같은 관계(엄마)로 연결된 보호자가 있습니다." } }
```

**프론트에서 할 일**: 학부모 연결 생성/수정 폼에서 이 `VALIDATION_ERROR` 응답을 그대로 사용자에게
보여주면 됩니다(다른 422 처리와 동일 패턴). 추가로, 관계(father/mother/other) 선택 UI에서 그
학생에 이미 등록된 타입을 알고 있다면 미리 비활성화해주면 더 친절합니다 — 다만 이건 필수는 아니고,
에러 메시지만 제대로 떠도 충분합니다.

**"Admin계정에서 연결할 수 없다고 뜸" 자체는 재현이 안 됐습니다** — `POST /v1/parent-links`를 API로
직접 호출하면 정상적으로 두 번째 부모(다른 relationType)를 연결할 수 있습니다. 짐작에는
`AccountManagementPage`/`StudentManagementPage`에 "이미 등록된 학생에 부모를 추가로 연결"하는 UI
자체가 아직 없어서(README의 "Not done" 목록에도 편집 플로우 미비가 적혀 있음) 그런 걸로 보입니다.
그 UI를 만들 때 `POST /v1/parent-links` (`parentUserId`, `studentId`, `relationType`)를 쓰면 됩니다.

## 2. 학부모 화면 상단 배너에 조회 중인 학생 표시 — 프론트 작업

`AppLayout` 상단 배너에 현재 보고 있는 자녀 이름/학년/반을 표시해주세요. 이미 화면에서 쓰고 있는
`GET /v1/students/{id}` 또는 `GET /v1/students/{id}/summary` 응답의 `name`/`grade`/`className`을
그대로 쓰면 되고, 백엔드 변경은 필요 없습니다.

## 3. 자녀 2명 이상일 때 전환(토글) UI — 프론트 작업

백엔드는 이미 다자녀를 지원합니다:
- 로그인 응답 `user.hasMultipleChildren` — 토글 UI를 보여줄지 여부 판단용
- `GET /v1/me/children` — 자녀 전체 목록(`studentId`, `name`, `grade`, `className`, `relationType`)
- 자녀별 데이터 조회는 각 API의 URL에 있는 `studentId`를 바꿔서 호출(예: `/students/{id}/homework`) —
  전역 헤더가 필요한 건 공지 API(`X-Active-Student-Id`, §12)뿐이고 나머지는 URL 파라미터로 충분

README에 이미 `ChildSelectPage`(SCR-17)와 `activeStudentStore.ts`가 스캐폴딩돼 있다고 적혀 있으니
그 페이지/스토어를 실제 토글 UI(상단 배너 드롭다운 등)로 연결하면 됩니다.

**테스트용 다자녀 계정**: `parent1`(오미영, 자녀 오지훈+문지우), `parent2`(한동현, 자녀 한서준+남궁민)
— 비밀번호는 `Parent1234!`.

## 4. 학부모에게 숙제가 안 보임 — 백엔드에서는 재현 안 됨, 프론트 확인 필요

**원래 피드백**: "선생님이 숙제 항목 추가 후 학생들 완료 체크를 했는데 학부모한테는 숙제가 안 보임."

백엔드에서 직접 재현해봤습니다 — 선생님 계정으로 `POST /v1/homework-items`(반 단위) →
`POST /v1/homework-records/bulk`로 완료 체크 → 그 학생의 학부모 계정으로
`GET /v1/students/{id}/homework?from=...&to=...` 호출 — **정상적으로 방금 만든 숙제가 응답에
포함됩니다.** 그래서 서버 쪽 문제는 아닌 것 같고, 프론트에서 아래를 확인해보시면 좋겠습니다:

- `from`/`to` 쿼리 파라미터가 필수인데, 화면에서 기본으로 보여주는 기간이 실제 숙제
  `assignedDate`를 포함하는 범위인지 (예: 최근 1주일만 기본 조회하는데 숙제는 그 밖의 날짜)
- 조회에 쓰는 `studentId`가 실제로 그 숙제를 체크받은 학생과 일치하는지 — 3번 항목(다자녀 전환)이
  아직 없는 상태라면, 부모가 보고 있는 자녀와 실제 체크된 자녀가 다를 수 있습니다(원인이 3번과
  연결돼 있을 가능성)
- 네트워크 탭에서 실제 응답의 `data` 배열이 비어 있는지, 아니면 응답은 정상인데 화면 렌더링에서
  누락되는지

재현되면 알려주세요 — 구체적인 요청/응답을 보면 바로 원인을 좁힐 수 있습니다.

### 4-1. 추가 조사 (2026-09-16) — "숙제 이력을 불러오지 못했습니다" 에러

데모에서 부모 계정으로 학생 조회 시 이 에러가 뜬다는 리포트가 와서 `GET /v1/students/{id}/homework`를
다시 여러 케이스로 직접 호출해봤습니다. **정상 요청(`from`/`to`를 올바른 `YYYY-MM-DD`로 채워서 호출)은
여전히 200으로 잘 옵니다.** 대신 아래 케이스들에서 에러가 나는 걸 확인했는데, 프론트가 이 중 하나에
해당하는 요청을 보내고 있을 가능성이 높습니다 — 특히 **①번(파라미터 누락)이 제일 의심됩니다.**

| 상황 | 응답 |
|---|---|
| ① `from`/`to` 아예 안 보냄 | `422 VALIDATION_ERROR` "필수 파라미터가 누락되었습니다: from" (`to`만 빠지면 `to`로) |
| ② 날짜 형식이 `YYYY-MM-DD`가 아님 (예: `2026/09/01`) | `422 VALIDATION_ERROR` "from 파라미터의 형식이 올바르지 않습니다." |
| ③ 그 부모의 자녀가 아닌 studentId로 조회 | `403 FORBIDDEN_SCOPE` "해당 학생의 데이터에는 접근할 수 없습니다." |
| ④ 토큰 없이/만료된 토큰으로 요청 | `401 UNAUTHENTICATED` |

**①이 제일 유력한 이유**: `from`/`to`는 스펙상 필수 쿼리 파라미터인데, 화면에 별도 날짜 선택 UI 없이
"최근 숙제" 개념으로만 부르는 화면이라면 프론트에서 아예 안 보내고 있을 수 있습니다. 이 경우 백엔드는
(의도대로) 422를 주는데, 프론트가 이 에러를 캐치해서 그대로 "숙제 이력을 불러오지 못했습니다" 같은
범용 에러 문구로 보여주고 있을 가능성이 큽니다.

③도 배제할 수 없습니다 — 3번 항목(다자녀 전환)이 아직 없어서, 다자녀 부모가 화면에 하드코딩되었거나
잘못된 studentId로 요청하면 403이 뜨고 이것도 같은 범용 에러 문구로 보일 수 있습니다.

**확인 요청**: 브라우저 네트워크 탭에서 이 요청의 실제 URL(쿼리 파라미터 포함)과 응답 상태 코드를
확인해서 알려주시면, 위 표 중 어디에 해당하는지 바로 알 수 있습니다. `from`/`to`를 안 보내고 있는 게
맞다면, 백엔드에서 이 둘을 선택 파라미터로 바꾸고 기본값(예: 최근 3개월)을 주는 것도 가능합니다 —
필요하면 요청해주세요.
